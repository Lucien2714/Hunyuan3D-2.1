# 0002 不需要训练的多图基线

## 背景

`0001-unposed-image-set-input.md` 定下多视图输入是同一物体的一组不带方位的图片，并决定先做不训练的基线，在服务器上看到效果后再决定要不要微调。本记录补充 0001，写这个基线在推理上的几项选择。

约束：

- 官方 2.1 只有单图的几何权重。去噪网络 `HunYuanDiTPlain` 经交叉注意力读条件 token，交叉注意力按实际的条件长度构造 K/V；官方配置关闭了固定长度的 `AttentionPool` 和 decoupled CA。
- 上游 `Hunyuan3DDiTFlowMatchingPipeline` 把图片列表当作一批互不相干的物体，每张出一个模型。
- 只给一张图时，结果要和上游单图一样（`AGENTS.md` 的"和上游的关系"）。
- 上游的贴图模型在结构上能接多张参考图（参考分支按 `N_ref` 处理），但 `multiviewDiffusionNet.forward_one()` 只把第一张交给扩散管线和 DINOv2，`Hunyuan3DPaintPipeline.__call__` 传列表会报错。上游发布的贴图训练代码每次只用一张参考图。
- 开发机跑不了 2.1 的推理，下面各方案的效果都没有在真实权重上比较过。

## 考虑过的方案

**几何入口**

- **新增一个继承上游管线的类（`Hunyuan3DUnposedMultiViewPipeline`）。** 加载原样继承，单图直接交给父类。好处：不改上游的几何文件，单图行为自然不变；"一组图片"和上游"一批图片"的含义分开。代价：多一个公开类，以后的 gradio、HTTP 接入要改用它。
- **改上游 `Hunyuan3DDiTFlowMatchingPipeline.__call__` 或 `prepare_image()`，让列表表示一组图。** 好处：调用方不用换类。代价：上游的列表本来表示一批互不相干的图，改掉会改变已有调用方的结果，也要改上游文件。
- **用上游的 `MVImageProcessorV2` 和 `DinoImageEncoderMV`。** 代价：它们要求 `front/left/back/right` 视图名，并按方位加位置编码，和 0001 的约定冲突；2.1 的官方权重也没有这个编码器。

**几何的多图融合**

- **速度平均（`velocity_mean`）。** 每个时间步，每张图各自做一次条件前向，都用同一个 `x_t`，平均各图的条件速度，再和共用的无条件速度做 CFG，每步只推进一次 scheduler。好处：DiT 每次看到的条件长度和训练时一样（一张图的 1370 个 token），每张图在每一步都参与。代价：每步要做 N+1 次 batch 1 的前向（开 CFG 时），上游单图是 1 次 batch 2 的前向；各图的速度场直接平均，图之间有冲突时可能被抹平。
- **token 拼接（`token_concat`）。** 把各图的 DINOv2 token 沿序列维拼起来，每步只跑一次 DiT。好处：模型能在交叉注意力里同时比对各张图，耗时增加得少。代价：单图权重从没见过这么长的条件，效果难预料；交叉注意力的 K/V 长度随张数线性增长。
- **每步轮换一张图。** 好处：每步只做一次条件前向。代价：会把某张图和特定的噪声阶段绑定，步数不能被张数整除时各图参与的次数也不同。

**张数上限**

- 不设上限：显存和耗时无法预期，出错时也不清楚是张数还是别的原因。
- 设一个首版上限（4），在服务器上按实测再调：好处是实验范围明确；代价是上限要靠以后的实测来改。

**贴图的 DINOv2 条件**

- **全部参考图的 token。** 和参考分支看到的是同一组图，现有的投影层逐 token 处理，不用改层。代价：DINOv2 的 context token 随张数线性增长，显存要实测。
- **只用第一张。** 代价：DINOv2 条件取决于列表顺序，和"顺序不带含义"冲突，也丢掉只在其余图里看得到的颜色和部件。
- **对称汇聚（比如平均）。** 好处：长度不变。代价：要另外设计，平均后的特征是训练时没见过的分布。

**处理顺序**

- 按调用方给的顺序：浮点累加、注意力的求和顺序和贴图 VAE 取随机数的顺序都随之变化，同一组图换个顺序结果就不同。
- 按图片的像素内容排序后再处理：同一组图不管怎么排列，计算顺序都一样，可以复现。不用文件名或 Python 的 `hash()`（每个进程随机化）。

## 决定

- 几何新增 `hy3dshape/hy3dshape/multiview_pipeline.py` 的 `Hunyuan3DUnposedMultiViewPipeline`，继承 `Hunyuan3DDiTFlowMatchingPipeline`，只给一张图时直接调用父类的 `__call__`。不改上游的几何文件。
- 两种融合都提供，默认 `velocity_mean`，同时在服务器上测 `token_concat`，按实测的质量、耗时和显存再决定以后的默认值。每步轮换首版不做。
- 两个入口都限制 1～4 张，超出时报错，不截断。
- 贴图改 `textureGenPipeline.py` 和 `multiview_utils.py` 两个上游文件：`Hunyuan3DPaintPipeline` 的 `image_path` 接受 1～4 张图的列表；全部参考图都进参考分支和 DINOv2（全部 token）；末尾新增 `seed=0` 参数。只传一张图、不传 `seed` 时和上游一样。必须改上游文件，是因为现有的公开类本身传列表就会报错，另加一个旁路类修不好这个入口。
- 多张图时，几何按预处理后的像素、贴图按缩放后的像素排序后再处理，顺序不传给模型。
- 首版只接入 Python 接口和 `demo_multiview.py`，`gradio_app.py`、`api_server.py` 和 cat3d 等服务器结果出来后再定。

## 后果

- 多了一个公开的几何管线接口，`Hunyuan3DPaintPipeline.__call__` 多了一个参数、`image_path` 多了一种类型。以后改这些参数算架构层面的改动。
- 两种融合的效果、多张参考图对官方贴图权重的效果、多图的显存和耗时都还不知道，要用户在服务器上跑 `docs/usage.md` 的验证命令。如果基线效果不够好，再按 0001 的后果一节决定是否微调。
- 张数上限 4 写在两个入口的常量里，改上限时两处一起改，并更新 `docs/design.md`。
- `velocity_mean` 开 CFG 时每步做 N+1 次 batch 1 的前向，上游单图每步做 1 次 batch 2 的前向。4 张时前向调用次数是 5 比 1，DiT 处理的样本数是 5 比 2。实际耗时是多少倍没有实测，要在服务器上量。
- 重复的图片会被保留，相当于加大它的权重，调用方要自己去重。
- 贴图按像素内容排序意味着参考图的 VAE 随机数分配取决于图片内容，同一组图结果可复现，但加一张图可能改变其余各图拿到的随机数。
